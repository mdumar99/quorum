# ADR-0002: Migrations, data access and database roles

- **Status:** Accepted
- **Date:** 2026-11-14
- **Deciders:** mdumar99

## Context
Phase 0 shipped without a schema. `ping_postgres` opens a connection per call, and the API connects as the bootstrap role, which is a superuser (`rolsuper = t` in `pg_roles`). Neither mattered while the only query was a health ping. Phase 1 adds the first real tables, including an audit log that must not be rewritable, and that forces three decisions that constrain each other: how schema changes are applied (and how grants travel with them), how the API talks to the database (connections, transactions, error handling), and which database identity the API runs as. This ADR records them together because the answers interlock. The migration tool decides whether grants are versioned, the access layer decides how transactions and locks are expressed, and the role split decides what a compromised API process can do.

## Decision

### 1. Migrations: Alembic, hand-written
- Runs as the owner role. The owner URL comes from its own variable and is never present in the API's `Settings` or the `api` service's environment. The test fixtures' owner connection comes from test configuration, not from `Settings`, and should not be added there later.
- Where it runs: not in the `api` container, which never holds the owner URL. One-shot compose services run the bootstrap and then the migrations as the owner, and `api` waits for them with `depends_on: condition: service_completed_successfully`. The migration step is built from the same image as `api`, so Alembic and SQLAlchemy ship in the API image too. The bootstrap spike (check B1) showed that a one-shot bootstrap service held back in this way keeps `api` from starting until it exits 0. It did not run migrations, and it ran from cached images, so it says nothing about the current code on `main`. The infra ticket's acceptance criteria include `docker compose up -d --build --wait` returning 0.
- No autogenerate and no `alembic check`. Drift is detected by applying `head` to an empty database and diffing `pg_dump --schema-only` against a committed `schema.sql`. Reason: autogenerate does not see grants or default privileges, which carry the governance weight, so even with metadata available it would miss exactly what matters.
- The diff must compare like with like. Role names are fixed constants and only passwords vary, because the dump contains `OWNER TO <owner>` and `GRANT … TO <app role>` lines and a different name in someone's local `.env` would fail the diff without any drift. Recent `pg_dump` releases also emit a random `\restrict` key per run in plain-format output, which has to be pinned with `--restrict-key` or stripped before diffing (see "Open before Accepted"). The Postgres image is pinned to an exact minor version, 17.11 (the version the spike ran), in Compose and CI, and the dump runs inside the container, so a cached local image and CI cannot differ; the pin itself is made in the infra ticket.
- Alembic's version table lives in its own schema (`version_table_schema`), created by the bootstrap, so the app role has no grants there. This holds only because default privileges are scoped to `IN SCHEMA public` (Decision 3).
- Migrations are forward-only. A downgrade path is a second code path that nothing in CI exercises (the drift check only applies `head` to an empty database), and for tables like `audit_log` an automatic "undo" would mean deleting rows that policy says are never deleted. A mistake is corrected by a new migration that moves forward, which also preserves the history of what the schema was and when it changed. Postgres DDL is transactional, so a failed migration rolls back instead of leaving a half-applied schema. The exceptions are statements that cannot run inside a transaction, such as `CREATE INDEX CONCURRENTLY`.
- Why Alembic, and why without autogenerate: Alembic gives ordered revisions, a version table recording what has been applied, and one command to bring a database to `head`, while still letting each migration be plain SQL via `op.execute`. Autogenerate is off for the reason above: it cannot see grants or default privileges. A plain SQL-file runner was rejected because we would have to build and test version tracking and ordering ourselves; Alembic already provides them, and the cost is a SQLAlchemy dependency that only the migration path uses, but that ships in the API image too, because the migration step is built from that image.

### 2. Data access: raw psycopg 3 with `psycopg_pool`
- No ORM and no SQLAlchemy Core. Rows map into Pydantic models with `class_row`.
- `/health` keeps its own connection; its contract is unchanged.
- Startup behaviour with the database down is not settled by this ADR. The bootstrap spike (P1-2, check B3) opened a `psycopg_pool` `AsyncConnectionPool` (4 connections) with `open(wait=False)` in the lifespan while the database was down. `/health` stayed 503 and under 3 s, but the Redis check failed intermittently (19 of 60 calls, against 0 of 51 without the pool) and Uvicorn began listening 3.9 s and 7.1 s late. The cause is a hypothesis, not tested. A smaller pool, fewer workers, lazy open and an IP address instead of the hostname were not tested. The data-access ticket must test them and record the result.
- Pool checkout timeout is set explicitly, below the pipeline deadline (the ordering invariant is in ADR-0004, Decision 1). A connection is never held across the LLM call.
- Time comes from the database. `as_of` and staleness checks both use Postgres `now()` (the transaction start time, which is fine with short transactions), so the system has one clock, not two.
- The libpq-style URL is used everywhere; only Alembic's `env.py` rewrites it for SQLAlchemy.
- Why raw over the ORM and over Core: the schema is built around insert-only tables, column-level `UPDATE` grants, explicit locks and savepoints, and an ORM's mutable entities and unit of work work against that grain. With only a handful of tables, relationships would buy little. Core was the closer call. It can express the Postgres-specific parts natively, so this is not about capability. Those parts (a partial unique index, `FOR UPDATE`, SQLSTATE handling, database-clock staleness checks) are the core of this schema, and Core would be a second notation for what is already Postgres SQL across a handful of tables. Raw SQL keeps those statements visible in one repository module, and psycopg is already a dependency through the health check. Core's other benefit, metadata-driven autogenerate, would not see grants or default privileges, so it would miss the parts of the schema that carry the governance weight.

### 3. Roles: owner and app role, privileges only (no trigger)
- Owner role `quorum_owner`: a non-superuser created by the bootstrap superuser, used for bootstrap and migrations only. App role `quorum_app`: non-superuser, non-owner, used by the API only. The role names are fixed constants, so the drift check does not depend on the configurable `POSTGRES_USER`, and the bootstrap superuser runs only the bootstrap.
- Default privileges are set `FOR ROLE <owner> IN SCHEMA public` and grant the app role `SELECT, INSERT` on future tables; `UPDATE` is an explicit column-level opt-in; `DELETE` and `TRUNCATE` are never granted. The `IN SCHEMA public` scope is what keeps Alembic's version-table schema out of the app role's reach (Decision 1).
- Identity columns are `GENERATED ALWAYS AS IDENTITY` (used for `audit_log`; `returns` uses UUID keys, see ADR-0004). The bootstrap spike (check B5) showed that the default table-level `INSERT` grant is enough for such a column, with no sequence grant. `serial`, `bigserial`, `GENERATED BY DEFAULT` and explicit `nextval()` are not used, because they were not tested.
- Columns that must never change after the first insert (`as_of`, `policy_version`, the fact snapshot) are left out of every `UPDATE` grant, so the database, not code review, enforces "reused on retry". The exact column list is in ADR-0004, Decision 6.
- "Append-only" means rows cannot be rewritten, not that every row is true. An app role with `INSERT` can still insert a false audit row. Detecting that is not a Phase 1 goal.
- Role bootstrap is idempotent and runs before migrations. It connects over the compose network: the official postgres image trusts the local socket and loopback, so a connection from there does not check the password, and the same applies to privilege tests. `quorum_owner` is given `CREATE` on schema `public` explicitly (USAGE comes from PUBLIC, CREATE does not). The bootstrap never changes the password of an existing role; a password-change path is left to the infra ticket.
- Limitation: whoever holds the owner or bootstrap-superuser password can still alter the schema and the grants, so this protects against the application, not against that person. The owner is not a superuser, which narrows the exposure. The Phase 2 hash chain addresses that.
- Fallback, not triggered (the bootstrap spike succeeded, see "Open before Accepted"): a trigger on `audit_log`, added on top of the role split and not instead of it. It guards against bugs, not compromise.
- Why privileges over a trigger: a trigger fires even for superusers, but it guards against bugs in our own code, not against compromise. Whoever connects as the owner can drop or disable it, and a superuser can bypass it with `session_replication_role`. While the API is a superuser, a trigger-only design leaves the real exposure in place. Privileges close it at the source: a non-superuser, non-owner app role cannot alter the table or issue `UPDATE`, `DELETE` or `TRUNCATE` on `audit_log`, and the failure is a `permission denied` error that a test can provoke. One mechanism is also easier to prove, by attempting the forbidden statements as the app role, than two layered ones. A trigger remains available as a later addition or as the fallback above.

## Consequences
### Positive
- The API process cannot alter or delete audit rows. The database enforces it, and tests prove it by attempting each forbidden statement as the app role.
- A compromised API process no longer holds superuser rights or the owner credentials, because the owner URL never reaches it.
- Grants are versioned with the schema and covered by the drift check. `pg_dump` dumps privileges by default and only `--no-privileges` omits them, so the command must not use that flag.
- Every statement is visible SQL in one module, with transaction boundaries, locks and savepoints stated explicitly.

### Negative / trade-offs
- Two credentials in `.env.example` and test configuration. `Settings` holds only the app-role URL.
- Grants become part of every schema change.
- A bootstrap step must work on fresh CI databases and on existing dev volumes.
- Hand-written migrations and queries get no autogenerate and no compile-time checking. The integration tests, run as the app role, are what catch mistakes.
- The drift check is a textual diff, so it breaks on anything that is not drift: a different `pg_dump` version, role names that vary with local configuration, or a random `\restrict` key. Role names are therefore fixed, and `pg_dump` must run with the Postgres version that Compose and CI use.
- SQLAlchemy is installed because Alembic requires it, and it ships in the API image (the migration step is built from that image) even though only migrations use it.
- Forward-only migrations mean a mistake is fixed by another migration, never by rolling back.
- Protection stops at the owner credentials. Detecting tampering by someone who holds them is deferred to the Phase 2 hash chain.

## Open before Accepted
Per the ADR README, an ADR is Accepted when its PR merges and is not edited afterwards. These items can change a decision above, so the bootstrap spike settles them and the results are written into the text before the PR merges. Everything else (test cases, container wiring details) lives in ticket acceptance criteria.
- [x] Bootstrap feasibility within one working session: an idempotent role bootstrap that works on fresh CI databases and on an existing dev volume. If it overruns, Decision 3 switches to the trigger fallback and this ADR says so. Result: the bootstrap ran idempotently on a fresh database (the throwaway spike volume) and on the existing dev volume (spike P1-2, check B2): every run exited 0 and a second run changed nothing. How long it took against the one-session limit was not recorded, and no fallback was needed. See the [#38 closing comment](https://github.com/mdumar99/quorum/issues/38#issuecomment-6729795780).
- [x] The pool opens without blocking startup when the database is down (Decision 2). Result: not met as tested (spike P1-2, check B3), so Decision 2 is reworded. See the [#38 closing comment](https://github.com/mdumar99/quorum/issues/38#issuecomment-6729795780).
- [x] `pg_dump` determinism: pin the `\restrict` key with `--restrict-key` or strip those lines, and confirm two runs with the Compose/CI Postgres version produce identical output. The `pg_dump` docs describe `--restrict-key` and a random key by default but not the release that introduced them; a third-party issue puts it at 17.6. Result: `pg_dump` is 17.11 in the local and the registry image. Two runs with `--restrict-key=<fixed value>` gave identical output, and stripping the `\restrict` and `\unrestrict` lines also gave identical dumps (spike P1-2, check B4). The release that introduced `--restrict-key` was not checked. See the [#38 closing comment](https://github.com/mdumar99/quorum/issues/38#issuecomment-6729795780).

## Alternatives considered
| Decision | Alternative | Why not chosen |
|---|---|---|
| Append-only | Trigger only | Guards against our own bugs but not against a compromised app: while the API is a superuser or owner, it can disable or drop the trigger. It also leaves the superuser API in place. Kept as the fallback in Decision 3. |
| Append-only | Trigger plus privileges | Privileges already deny `UPDATE`, `DELETE` and `TRUNCATE` to the app role, so a trigger adds a second mechanism to build and test with no extra protection against the app. It would only help against the owner, who can drop it. Depth can be added later if wanted. |
| Migrations | Hand-written SQL scripts | We would have to build and test version tracking and ordering ourselves. Alembic provides both and still lets migrations be plain SQL; the cost we accept is the SQLAlchemy dependency. |
| Migrations | Autogenerate plus `alembic check` for drift | Cannot see grants or default privileges, so even with metadata it would miss the parts of the schema that carry the governance weight. The `pg_dump` diff covers them. |
| Migrations | Reversible (up/down) migrations with a roundtrip check | An earlier plan included a roundtrip check. Dropped: a downgrade is a second code path nothing else exercises, and for audit data "undo" would delete rows that are never deleted. Forward-only fixes are recorded as new migrations. |
| Data access | ORM | Mutable entities and a unit of work work against insert-only tables, column-level `UPDATE` grants, explicit locks and savepoints, and relationships buy little with a handful of tables. |
| Data access | SQLAlchemy Core | Not a capability gap, since it can express the Postgres-specific parts natively. It would be a second notation for what is already Postgres SQL across a handful of tables, and its metadata-driven autogenerate would not see grants or default privileges. The closer call. |
